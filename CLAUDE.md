- Quatre principes : accès limité au lieu rejoint ; aucun droit à une réponse ; parcours simple

Mises à jour sans passer par le store (`expo-updates`, `runtimeVersion: fingerprint`, canal `production`) : workflow manuel `.github/workflows/mobile-update.yml` pour le script de la coquille seulement ; toute partie native ou permission nouvelle exige un build et le store. ## Supabase (projet `blqcmpqctetmjqsfdvsq` « ProRod », Paris) — jamais un autre projet Supabase
- Schéma : `db/accounts-and-venues.sql` (tables, RLS, stockage) + `db/functions.sql` (toutes les fonctions, exportées du projet, à régénérer après chaque migration : `docs/verification-log.md`) ; tests transactionnels `db/verify-accounts-and-venues.sql` (tout est annulé en fin de script), résultats consignés dans `docs/verification-log.md`.
- Modèle : tables publiques `profiles` et `venue_sessions` en lecture seule pour l'utilisateur
  (RLS) ; schéma `private` (lieux, invitations hachées, restrictions) inaccessible aux clients ;
  toute écriture passe par des fonctions `private.*` SECURITY DEFINER exposées par des
  wrappers `public.*`. Ne jamais autoriser depuis des métadonnées modifiables par l'utilisateur.
- Administration : `admin.html` (bundle `src/admin.js`), rôle = claim Auth `app_metadata.prod_admin = true`
  posé par l'opérateur dans Supabase (jamais `user_metadata`) ; validation en deux étapes exigée par défaut, réglage serveur `admin_two_step` (`db/2026-11-14-admin-two-step-switch.sql` ; la désactiver est une décision de l’exploitant, la CNIL recommande de la garder pour des données sensibles) (le portail l’enrôle à la première connexion) ; journal
  `private.admin_actions`. Invitations (QR) depuis le portail, ou `db/create-invite.sql` en secours.
- E-mails Auth : le service intégré de Supabase n'envoie qu'aux membres de l'organisation ;
  configurer le SMTP Brevo du projet + Site URL + redirections avant tout test avec le client.
- Comptes : trois types (`profiles.account_type` personal | pro | venue). Depuis le 13 nov. 2026 (demande du client), le type `venue` s’affiche « événement » / « event » partout dans l’app (le nom interne ne change pas), et un lieu peut être de type `event` (`db/2026-11-13-event-category.sql`). Les comptes établissement ne participent jamais aux rencontres (`private.require_person()`), gèrent leur lieu (candidature approuvée par l’admin, QR générés sur le téléphone, annonces, durée ≤ 3 h pour un compte événement ; depuis le 14 nov. 2026 l’administrateur choisit la durée de la visite à la génération de chaque QR code, de 15 min à 12 h : `venue_invites.duration_minutes`, `db/2026-11-14-qr-visit-length.sql`, vérifié par `db/verify-qr-visit-length.sql` ; un QR sans durée garde celle du lieu, plafonnée par `max_session_minutes`). Réglages serveur dans `private.app_settings` : `simulation`, `max_session_minutes`, `pass_rule` (everyone | none, jamais selon le genre), `feedback_email` / `feedback_sender` (jamais dans Git), `feedback_auto_email` (false = pas d’e-mail à chaque retour ; l’administrateur envoie tous les retours regroupés depuis l’onglet Retours, `admin_send_feedback`, `db/2026-11-14-feedback-digest.sql`). Clé Brevo pour les e-mails de retours : Vault, nom `brevo_api_key`.
- Connexion par téléphone : hook Supabase « Send SMS » → fonction Edge `supabase/functions/send-sms` (Brevo SMS transactionnel ; secrets `SEND_SMS_HOOK_SECRET` et `BREVO_API_KEY` côté Edge Functions). Boutons Google / téléphone activés par `providers` dans `src/public-config.js` une fois le fournisseur configuré dans Supabase.

Chaque photo choisie est testée par une petite lecture (`photoReadable`) ; en cas d’échec, un second bouton « Choisir depuis mes fichiers » ouvre l’explorateur de fichiers (champ sans `accept`, `#photo-files`, type vérifié ici). Corrigé côté site, sans nouveau build. Tests : `tests/photo-fallback.test.cjs`. Jamais vérifié sur un vrai Samsung depuis cet environnement : la confirmation vient du testeur.

- Sécurité (réunion du 10 nov. 2026) : un signalement bloque automatiquement la personne signalée pour celui qui signale (`report_member` → `block_member`) ; l’admin peut avertir (`admin_warn_member`, notification `account_warned`) ou suspendre ; fin de conversation avec raison (`end_conversation`, `closed_reason`), montrée en termes neutres. Taille facultative (`height_cm`, 120–230) affichée sur le profil. Photo de profil dans une épingle de localisation (`pinPhoto`).

Même règle pour tous ; le membre ne peut pas se masquer (annoncé à l’inscription et dans la politique de confidentialité). Depuis le 13 nov. 2026 (`db/2026-11-13-blurred-preview.sql`) : avant le pass, on montre une version floutée de la photo créée sur le téléphone du membre (20 px au départ ; 36 px depuis le 20 nov. 2026, demande du client pour deviner une silhouette : flou appliqué aux pixels enregistrés, `softenPixels`, anciens aperçus refaits à l’ouverture de l’app ; ne pas aller plus net sans avis juridique, le visage deviendrait reconnaissable) ; depuis le 17 nov. 2026 (`db/2026-11-17-blur-without-id.sql`) elle est stockée en ligne dans le profil (`avatar_blur`, data URL JPEG ≤ 6 000 caractères, `set_avatar_blur_data`) et renvoyée par `venue_members.blur_data`, sans nom de fichier ni identifiant (l’ancien chemin `u/<id>/blur-…` révélait l’id ; politique `avatars_blur_select` supprimée) ; jamais de flou côté client sur la vraie photo.

## Règles
- Dépôt public, destiné à être transféré au client : pas de secret, pas de donnée réelle, pas de nom de client,
  pas d'adresse privée dans le code ou l'historique.
- Toute fonction livrée doit marcher avec de vrais comptes et des contrôles côté serveur ;
  la démo ne vaut pas livraison. Ajouter un test pour chaque règle de sécurité.
- Textes FR/EN partout ; on pousse directement sur `main` après build + tests verts.
- Tutoiement (décision du client, 13 nov. 2026) : « tu » pour les comptes personnels et les visiteurs, « vous » pour les comptes professionnels et événement. Les textes français s’écrivent avec « vous » dans `src/account.js` ; la version « tu » de chaque phrase qui s’adresse au lecteur va dans `src/tu.js` (toute nouvelle phrase avec vous/votre/vos doit y être ajoutée). Conditions et politique de confidentialité : « vous ».
